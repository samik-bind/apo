List the tasks available to run, and say **where it listed them from** — the last line always names the source: the backend catalog (when a project is set and no explicit task root is given) or a local scan of `--dir`.

With a project set and the backend reachable, `apo task list` reads the backend's synced task inventory. Pass `--dir <path>` (or set `APO_TASK_ROOT`) and it scans that directory for `.eval.ts` files instead — the same root [`apo task run`](/cli/task-run/) resolves tasks against. If the task root doesn't exist, the command exits `2` instead of silently reporting an empty list.

## Synopsis

```bash
apo task list [--dir <path>] [--project <id>]
```

The `ID` is the task folder name — pass it to [`apo task run`](/cli/task-run/). For tasks grouped in subfolders, the id is **folder-scoped**: the name prefixed by its folder path (e.g. `chat/cost-inquiry`). The `Adapter` column shows the adapter's declared `name`. `Checks` is `yes` when the task registers any `test(...)` blocks, `-` when it has none.

:::tip[Not sure which universe you're in?]
`apo status` prints the effective backend, project, and task root. The trailing source line on every `task list` output is the quick answer: `backend catalog (project …)` or `scanned <path>`.
:::
